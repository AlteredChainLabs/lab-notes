# MathLab Lab Notes
**Date:** 2026-08-06

# Focus

Today we completed the first version of the **MathLabBench Experiment Engine**.

The goal of MathLabBench is **not** to solve mathematics problems or evaluate reasoning ability directly. Its purpose is to evaluate **pedagogical decision-making** in adaptive mathematical tutoring.

This separates the research problem ("How should an AI tutor teach?") from the infrastructure used to evaluate it.

---

# Major Milestone

MathLab is now naturally divided into two complementary systems:

```
MathLab
│
├── Tutor
│     Adaptive Socratic mathematical tutoring
│
└── MathLabBench
      Evaluation framework for tutoring policies
```

The tutor teaches students.

MathLabBench evaluates whether the tutoring policy actually improves.

---

# Implemented Today

## Experiment Engine

Designed the experiment hierarchy:

```
Experiment
│
├── Provider
├── Runs
├── Trajectories
│     └── Turns
│
└── Results
```

Instead of evaluating a single trajectory, MathLabBench now evaluates complete experiments.

---

## Experiment Types

Created:

- Experiment
- ExperimentResult
- ExperimentTrajectoryRun
- TrajectoryAggregate
- FailureModeCount

These structures separate:

- experiment configuration
- individual trajectory runs
- aggregate statistics
- failure analysis

---

## Generic Runner

Extended the evaluation runner.

Instead of only supporting

```
runTrajectory(...)
```

the system now supports

```
runExperiment(...)
```

which repeatedly executes trajectories and collects results.

---

## Aggregator

Implemented experiment aggregation.

Statistics now include:

- average learner-state score
- average intervention score
- average content score
- average overall score
- trajectory pass rate
- overall trajectory pass rate
- standard deviation
- infrastructure failure rate
- failure mode counts

Infrastructure failures are intentionally separated from pedagogical failures.

---

## Persistent Stuckness

Expanded evaluation of the original trajectory using repeated stochastic runs.

Result:

- learner-state classification remained extremely stable
- intervention selection was less consistent

The dominant failure mode:

```
turn-4

probe
```

instead of an expected stronger pedagogical intervention.

This indicates that the model often recognizes the learner's state correctly but does not consistently escalate assistance.

---

## New Benchmark

Added:

### Misdirection and Recovery

This trajectory evaluates whether the tutor can:

- recognize misconceptions
- avoid reinforcing incorrect reasoning
- guide the learner toward discovering the mistake
- recognize successful recovery
- avoid revealing the full solution

# Research Observation

One of today's most important findings:

The model appears significantly stronger at

```
diagnosing learner misconceptions
```

than at

```
adaptive intervention escalation.
```

This distinction would not have been discovered through a single evaluation run.

Repeated experiments revealed that learner-state assessment is highly stable while intervention selection remains stochastic.

# Architectural Decisions

## Research vs Infrastructure

Research target:

```
Adaptive pedagogical decision-making
```

Infrastructure:

```
Experiment Engine
```

The experiment engine exists to make pedagogical research measurable and reproducible.

---

## Provider Abstraction

The evaluation framework no longer depends directly on Gemma.

Instead it depends on

```
TutorProvider
```

Future providers may include:

- OpenAI
- Anthropic
- Local Ollama
- Rule-based tutoring policies
- Future MathLab policies

No evaluator changes should be required.

# Long-Term Vision

MathLabBench should not become a benchmark for language models.

It should become a benchmark for

```
adaptive pedagogical decision-making.
```

The benchmark should allow comparison between:

- prompting strategies
- tutoring policies
- learner-state models
- intervention-selection policies
- future AI tutors

using identical learner trajectories.
